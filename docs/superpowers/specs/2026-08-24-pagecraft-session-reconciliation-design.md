# PageCraft 会话完成态自动恢复设计

日期：2026-08-24  
目标分支：`lxy`

## 背景

PageCraft 当前依赖面板挂载期间观察 DSH 会话的 `running: false → true → false` 边沿来推进批次状态。当用户关闭 PageCraft、切回 DSH 查看 Agent 执行过程时，面板会被卸载；再次打开时只能读到当前的 `running=false`，无法知道期间曾经开始并完成过一次任务。结果是 Agent 已输出最终答复，而 PageCraft 历史仍停留在 `queued`（“进入队列”）。

## 目标

- PageCraft 面板在 Agent 执行期间可以任意关闭和重新打开。
- 重开后自动识别属于 PageCraft 批次的已完成 Agent turn。
- 自动刷新预览、捕获修改后截图并生成前后视觉对比。
- 同一批次只结算一次，不因重复打开或刷新而重复截图。
- 无充分证据时保持未完成状态，避免将其他会话任务误判为当前批次。
- 只修改 PageCraft `lxy` 分支，不修改 DSH 源码及其他分支。

## 非目标

- 不修改 DSH 的 Agent 协议或增加宿主回调。
- 不在 PageCraft 关闭后运行隐藏的后台轮询器。
- 不把所有会话中的普通 Agent 回复都视为 PageCraft 批次完成。

## 方案选择

采用“会话事实恢复”方案：发送时持久化批次身份和会话进度基线；运行时继续使用实时 `running` 信号；重开时使用 DSH 的队列、会话节点和已完成 turn 进行补偿判定。

不采用纯轮询，因为面板卸载后轮询停止，且仅凭 `running=false` 无法区分“尚未开始”和“已经完成”。不采用 Agent 主动回调，因为这会扩大到 DSH/Agent 协议修改，并提高部署门槛。

## 数据模型

为视觉批次增加可选的会话关联信息：

- `submittedAt`：成功提交到 DSH 的时间。
- `baselineCompletedTurn`：提交前已完成的最大 turn 序号；没有完成 turn 时为空。
- `observedRunning`：PageCraft 是否曾观察到该批次运行。
- `settledTurn`：恢复判定确认的完成 turn 序号。

新增字段必须保持可选，以兼容旧版 IndexedDB 中已经存在的历史记录。旧批次可通过批次 ID 和提交时间进行保守恢复；证据不足时不自动完成。

## 完成态判定

一个 `queued` 或 `running` 批次只有同时满足以下条件，才能自动进入修改后截图阶段：

1. 当前 Agent 不在运行。
2. DSH 瞬时队列中不再包含带有该 `batchId` 的 PageCraft 请求。
3. 会话内容中可以找到该 `batchId` 对应的用户请求，证明任务确实进入了当前会话。
4. 在请求之后存在已完成的 Agent turn；对于新批次，该 turn 必须晚于发送前基线。
5. 批次尚未进入 `capturing-after`、`completed`、`failed` 或 `rolled-back` 等终态。

若只观察到 Agent 正在运行，则将 `queued` 推进为 `running` 并记录 `observedRunning=true`。若 Agent 已停止但无法把完成 turn 与批次关联，状态保持不变，并允许用户触发“重新检测”。

## 状态流

```text
draft
  → capturing-before
  → queued
  → running                 （实时观察或重开恢复）
  → capturing-after         （完成态证据成立）
  → completed
```

异常路径保持现有 `failed` 状态；恢复和截图失败时记录错误，但不伪造 `completed`。

## 运行流程

### 发送时

1. 读取会话快照并记录发送前最大完成 turn。
2. 创建并持久化批次及其 `batchId`。
3. 把带有 `batchId` 的提示发送到 DSH 队列。
4. 提交成功后写入 `submittedAt` 和基线。

### 面板保持打开

继续监听 `session.subscribe()`：

- `running=true`：将相关批次推进为 `running`。
- `running=false`：通过统一的恢复判定器确认归属，再进入修改后截图。

### 面板重新打开

1. 读取所有未结算批次。
2. 从最新会话快照构造可查询的队列、消息和完成 turn 事实。
3. 按创建顺序逐个恢复，避免多个排队批次抢占同一个完成 turn。
4. 对第一个证据完备的批次执行 `capturing-after`。
5. 刷新 iframe，加载完成后截图并生成对比记录。

## 并发与幂等

- 使用现有活动批次引用和恢复互斥锁，保证同一时间只结算一个批次。
- 状态转移前重新读取持久化记录，只有 `queued/running` 才能进入恢复路径。
- `settledTurn` 不能分配给多个批次。
- 重复订阅通知、React Strict Mode 重放或反复打开面板均不得重复生成修改后截图。

## 用户界面

- 恢复开始：`检测到 Agent 已完成，正在同步最新页面…`
- 捕获阶段：进度卡推进到“验证结果/完成同步”。
- 证据不足：保留当前阶段，显示“尚未确认该批次已完成”，并提供“重新检测”。
- 完成：历史中可查看修改前后截图及回滚入口。

## 错误处理

- 会话快照暂不可用：保持原状态，下次订阅通知或重开时重试。
- 预览刷新失败：批次保留在可重试状态，并展示明确错误。
- 修改后截图失败：记录截图错误，不丢失修改前材料和批次关联信息。
- Agent 报错：若会话暴露对应错误，则批次进入 `failed`，不生成成功对比。

## 测试

单元测试覆盖：

- 面板保持打开时的正常 `queued → running → completed`。
- Agent 执行期间关闭面板，完成后重开自动结算。
- 打开时任务仍在队列或仍在运行，不提前完成。
- 无 `batchId`、无新增完成 turn 或属于其他任务时不误判。
- 多个 PageCraft 批次按顺序关联各自完成 turn。
- 重复恢复调用保持幂等。
- 旧版历史记录字段缺失时兼容读取。

集成验证覆盖：

1. 从 PageCraft 发送一条页面修改评注。
2. 关闭 PageCraft，在 DSH 等待 Agent 完成。
3. 再次打开 PageCraft。
4. 确认右侧自动从等待态推进到同步与完成。
5. 确认预览显示新页面，历史中存在前后对比且可回滚。
